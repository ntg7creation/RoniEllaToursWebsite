# Future leads, CRM and internal website

This starter keeps enquiry handling separate from delivery but has no saved leads. Its enquiry ID is a correlation value, not a database record. The office inbox and provider are the only current recipients of contact data.

1. **Persistent enquiries:** add a managed database, migrations, retention/deletion rules and explicit consent policy versions. Store enquiries and a durable idempotency record atomically. Decide whether acceptance will mean saved enquiry rather than email acceptance; version/document that contract. Preserve first-created timestamps and canonical IDs.
2. **Reliable delivery and CRM:** use a transactional outbox committed with the lead; run a separately scheduled durable worker/queue with bounded exponential backoff, dead-letter handling, alerts and manual replay. Never rely on work continuing after a Vercel response. Track attempts and provider IDs, validate webhook signatures/replays, and distinguish accepted, delivered, bounced and failed. Make CRM upserts idempotent by canonical lead ID; reconcile outages and duplicates. Restrict provider scopes and configure retention. Gmail API is a possible replacement adapter, but has different authorization, quotas and retry semantics; do not assume Resend's idempotency contract transfers to it.
3. **Separate internal staff website:** authenticate staff through an established identity provider with MFA and short sessions. Enforce authorization on every backend operation, not only in UI/CORS. Add CSRF controls if using cookie sessions and separate public submission from staff routes. No public lead-listing endpoint is planned.
4. **Permissions:** enquiry agents read/update assigned leads; supervisors assign/export with explicit permissions; content editors draft copy; publishers approve/publish; administrators manage access. Apply least privilege and field-level restrictions where needed. Record append-only audit history for reads/exports where appropriate, lead changes, assignments, access changes and content publication: actor, time, action, record/version, reason and safe diff. Limit sensitive values in audit records; restrict audit access and define retention.

## One authoritative content source

Today `src/content/` owns routes, tour slugs, media URLs, itinerary structure and archive/source metadata. Display copy lives in matching `src/locales/he/*.json` and `src/locales/en/*.json`, including per-tour/article catalogs. For example `contact.json` has the same Hebrew lookup keys in both languages but different values. Keys are stable identities, not proof that Hebrew is the translation source. English is the explicit source for automatic translations into Russian/other unauthored languages. Placeholders such as `{field}` must survive translation.

Initially, keep these version-controlled files authoritative. A future internal editor can create reviewed changes to that source with validation and preview. Do not create an independent editable database and continue editing JSON manually as competing authorities.

If moving to a CMS/database later, migrate to one versioned content model keyed by stable page/block IDs. Store shared facts (dates, prices, route IDs, structure) once, with authored Hebrew and English variants on the same record, English automatic-translation source revision, translation-review status and provenance. Generate the existing JSON/module artifacts from that authority for compatibility, or have the frontend consume published snapshots; generated artifacts must no longer be manually edited. Preserve lookup-key mappings during migration, validate locale key parity, interpolation tokens and RTL/LTR behavior, invalidate translation caches by published source hash and flag stale translations when source changes. Use drafts, preview, review/publish permissions, audit history, rollback and optimistic concurrency. Do not silently replace reviewed Hebrew/English copy with automatic translation.

No database, worker, CRM, authentication, staff UI, editing API or CMS is implemented in this phase.
